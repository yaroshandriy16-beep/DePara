# ДеПара

Базовий Telegram Mini App для студентів і викладачів на React, TypeScript та Vite.

## Локальний запуск

Потрібні Node.js та npm. У корені проєкту виконайте:

```bash
npm install
npm run dev
```

Відкрийте адресу, яку виведе Vite, у браузері. Інтерфейс працює і поза Telegram; у такому разі дані профілю Telegram недоступні.

Перевірка типів і production-збірка:

```bash
npm run build
```

Щоб перевірити застосунок саме всередині Telegram, його потрібно розмістити за доступною HTTPS-адресою та відкрити як Mini App через налаштованого бота. Це потребує окремого налаштування; проєкт не змінює бота і не публікує застосунок автоматично.

## Дані та інтеграції

Заняття у `src/data/schedule.ts` демонстраційні й не є розкладом ВНАУ. Для ВНАУ підключено окремий сервер, який отримує та перевіряє відкриті розклади МКР. Див. розділ «Підготовлений тестовий Worker для ВНАУ» нижче.

Telegram Web App bridge підключено в `index.html`, а роботу з профілем винесено у `src/lib/telegram.ts`. Ім’я та фото з `initDataUnsafe` використовуються тільки для відображення. Цим неперевіреним даним не можна довіряти для авторизації; для неї потрібна перевірка підписаних даних Telegram на сервері.

## Публікація на GitHub Pages

Проєкт підготовлено для GitHub Pages, зокрема для адреси з назвою репозиторію в шляху. Для публікації потрібен репозиторій на GitHub, де дозволено використання Pages. Після завантаження коду в репозиторій:

1. У **Settings → Pages → Build and deployment** оберіть джерело **GitHub Actions**.
2. У вкладці **Actions** відкрийте **Deploy to GitHub Pages** і запустіть **Run workflow**. Публікація запускається вручну, а не при кожному push.
3. Після успішного виконання відкрийте HTTPS-адресу, показану в результаті workflow або в налаштуваннях Pages. Сайт GitHub Pages може бути загальнодоступним.
4. Використайте це посилання для налаштування Mini App у тестовому боті через BotFather. Основний бот змінювати не потрібно.

Файли workflow самі по собі не створюють репозиторій і не публікують сайт; для цього потрібні зазначені вище дії в GitHub.

## Друга ітерація

Під час першого входу можна обрати демонстраційний каталог або ВНАУ (для ВНАУ потрібен налаштований сервер). Вибір і оформлення зберігаються локально в браузері. Демонстраційний розклад повторюється за днями тижня і не є розкладом ВНАУ; погода для Вінниці отримується з Open-Meteo. Чисельник і знаменник ще не налаштовані. «Вікна» викладача обчислюються між заняттями обраного джерела. Зошит, чати й друзі поки не працюють.

Для перегляду на iPhone в одній мережі запустіть `npm run dev` на комп’ютері та відкрийте в Safari адресу мережі, яку покаже Vite. Це локальний перегляд у браузері, а не Telegram Mini App. Для тестування в Telegram потрібне доступне HTTPS-посилання на опубліковану версію.

## Екран «Сьогодні»

Активний студентський розклад можна змінити через назву групи. Додаткові групи та вибір зберігаються локально і не змінюють основну групу профілю. Дані демонстраційних занять доступні лише для групи МН-21; для інших демонстраційних груп застосунок показує, що дані недоступні. Для ВНАУ потрібен налаштований сервер.

Погода для Вінниці запитується з Open-Meteo без запиту геолокації. За відсутності відповіді використовується останній збережений результат із позначкою часу або показується недоступність. Погодні ефекти й анімації регулюються в профілі або у деталях погоди; системне налаштування зменшення руху також враховується.

## «Розклад» і поширення

На вкладці «Розклад» доступні календар тижня або місяця та вибір дня. Іконка поряд із заголовком відкриває стан обраного джерела. Даних для обчислення чисельника та знаменника немає. Кнопка поширення готує текст із заняттями обраного джерела на тиждень чи місяць. Вона використовує системне меню, якщо воно доступне, інакше пропонує копіювання тексту; публічний доступ до чужого розкладу не створюється.

## Підготовка інтеграції ВНАУ

В `integrations/vnau/` підготовлено отримання й перевірку відкритих таблиць МКР для груп і викладачів, а також обмежений ручний пілот. `src/data/vnau.ts` читає перевірені JSON через HTTPS із окремим кешем для кожної групи, викладача та періоду. Ні браузер, ні Telegram Mini App не звертаються безпосередньо до HTTP МКР.

Для локальних перевірок Python потрібне окреме віртуальне середовище:

```bash
python -m venv .venv
. .venv/bin/activate
pip install -r requirements-vnau.txt
python -m unittest discover -s tests -p 'test_vnau_*.py' -v
```

Ручний workflow `.github/workflows/vnau-diagnostic.yml` запускався для однієї групи й одного викладача. Він не публікує застосунок і не має автоматичного розкладу. Подальші кроки, перевірені обмеження джерела та умови ввімкнення описані в `integrations/vnau/INTEGRATION_PLAN.md`.


## Підготовлений тестовий Worker для ВНАУ

`integrations/vnau/cloudflare/` містить Worker для тестування на безкоштовному тарифі Cloudflare з одним спільним SQLite-кешем і контролем частоти звернень до МКР. Локальний runtime workerd і розгорнутий тестовий Worker перевірено на відкритих даних МКР. З'єднання користувача з Worker використовує HTTPS, проте сам МКР працює через HTTP. Telegram-боти при цьому не змінюються.

Cloudflare під час тесту повернув HTTP 530 для `mkr.vsau.org`, хоча публічний DNS указував на IP МКР `81.30.162.30`. Підготовлений транспорт використовує DNS-ім'я `81.30.162.30.sslip.io` для прямого з'єднання з тим самим IP; це сторонній DNS, а не сервер-проксі. Перед зверненням обидва імені перевіряються через DNS-over-HTTPS Cloudflare; при зміні IP інтеграція зупиняється, поки адресу не перевірять. У DNS-запитах немає пошукового запиту викладача або назви вибраної групи. Оскільки МКР використовує HTTP, шифрування між Worker і МКР немає; наявність DNS-перевірки не замінює HTTPS.

Тестова збірка існуючого застосунку та API в один Worker, **без публікації**:

```bash
VITE_VNAU_API_ORIGIN=https://test-example.workers.dev npm run build:cloudflare-preview
```

Вказати майбутній HTTPS origin тестового Worker; приклад — не чинна адреса. Файли потрапляють до ігнорованої Git папки `out/cloudflare-preview/`. Для перевірки парсера, форм і кешу через окремо встановлений workerd використайте `mkdir -p out/workerd-test`, а потім `workerd test --experimental -d test-storage=out/workerd-test tests/vnau-cloudflare.capnp`. Додавати workerd до залежностей застосунку не потрібно.

У тестовому варіанті спільний кеш обмежено 512 записами та 5 МіБ JSON, а одну відповідь — 1 МіБ; невикористані щонайменше 30 днів записи очищаються через alarm, а при переповненні найстаріші можуть видалятися раніше. Час використання оновлюється не частіше разу на день, тому очищення за віком відбувається приблизно через 30–31 день. SQLite також потребує службового місця. На телефоні після успішного збереження нового розкладу так само очищаються старі копії та найстаріші копії понад 20 записів або 1 МіБ; налаштування профілю не видаляються. Цю політику погоджено для тесту. Архів старих розкладів не створюється; вони доступні, доки дані є у ВНАУ або тимчасовому кеші. Майбутні фонові сповіщення ще не реалізовані.

## Альтернативний Python-сервер ВНАУ

Локальна серверна частина — `integrations/vnau/server.py`. Вона виконує перевірений пошук викладачів та каскадний вибір факультету, курсу й групи, отримує розклади через публічні форми МКР та повертає лише перевірений JSON. МКР доступний через HTTP, тому браузер повинен спілкуватися **лише з HTTPS-сервером**, а не з МКР напряму. Сесійні cookie та CSRF залишаються на сервері.

Для локальної перевірки:

```bash
python -m venv .venv
. .venv/bin/activate
pip install -r requirements-vnau-server.txt
python -m unittest discover -s tests -p 'test_vnau_*.py'
python -m integrations.vnau.server
```

Вбудований сервер прив'язаний до `127.0.0.1` і призначений тільки для локальної розробки. Для розгортання потрібні HTTPS, контрольоване вихідне з'єднання до HTTP МКР та **постійне сховище** для `VNAU_CACHE_DIR`; без постійного сховища серверний кеш не переживе перезапуск. Задати `DEPARA_ALLOWED_ORIGINS=https://yaroshandriy16-beep.github.io`. Ручний workflow GitHub Pages збирає тестову версію з публічною адресою Cloudflare Worker у `VITE_VNAU_API_ORIGIN`; це не пароль і не токен. Щоб використовувати інший сервер, змініть цю адресу в workflow. Приклад запуску Python-сервера на Linux: `gunicorn integrations.vnau.server:application --workers 1 --threads 4 --timeout 150 --bind 0.0.0.0:$PORT`. Один процес обов'язковий для локального обмежувача запитів; масштабування на кілька процесів/інстансів потребує спільного обмежувача та сховища, а не зміни прапорця.

Пошук викладачів потребує щонайменше двох символів; якщо МКР повертає 200 або більше результатів, користувачеві пропонується уточнити запит. Усі дані йдуть через контрольований сервер; користувацькі дії не запускають GitHub Actions і не вимагають GitHub-токенів. Серверне отримання для кожного розкладу кешується дві години, виконується послідовно та обмежує кожен запит до МКР 14 днями. При помилці зберігається останній підтверджений діапазон із позначкою часу; дні поза ним не вважаються порожніми. Для захисту сховища задано межі кешу (5000 файлів і 128 МіБ); коли вони вичерпані, підтверджені дані не видаляються, а нові записи не створюються до обслуговування сховища.

Погоджено тестовий Worker та оновлення робочої гілки GitHub. Публікація в основній версії та зміни основного бота потребують окремого погодження.
