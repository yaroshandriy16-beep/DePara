# ВНАУ: перевірка та підготовка серверного підключення

Діагностичний workflow ручний. На прохання користувача підготовлено сервер для довільного пошуку груп і викладачів; погоджено його тестове розгортання в Cloudflare та оновлення робочої гілки GitHub. Основна версія Mini App залишається окремою. Не вносити cookies, CSRF, сирий HTML або приватні дані у репозиторій, логи чи публічні артефакти.

## Обраний варіант: запити через HTTPS-сервер

`integrations/vnau/server.py` надає каталог факультетів, курсів і груп, пошук викладачів та розклади за їхніми підтвердженими ID. Інтерфейс використовує публічний `VITE_VNAU_API_ORIGIN` лише після налаштування сервера. Вибір користувача залишається у браузері; GitHub Actions не запускається від дій користувача. Дані отримуються при відкритті і повторно не раніше ніж через дві години, а не збираються масово. Сервер приймає тільки обмежені запити і зберігає перевірений кеш окремо для груп, викладачів і діапазонів дат; відповіді за межами підтвердженого діапазону не вважаються порожнім розкладом.

Для публікації потрібні окремо погоджений HTTPS-хостинг, з'єднання з HTTP МКР та постійне сховище для кешу. Один процес сервера забезпечує локальне обмеження запитів; масштабування потребує спільного обмежувача та сховища. Після розгортання необхідно перевірити фактичний доступ хостингу до МКР, HTTPS, збереження кешу після перезапуску та Mini App на iPhone/Telegram. Деталі запуску наведено в README.

06.11.2026 локально підтверджено офіційну доменну адресу `http://mkr.vsau.org` (DNS повернув IP публічного МКР). Підготовлено альтернативний Worker `cloudflare/worker.mjs`: форми МКР і таблиці читаються у workerd, підтверджені результати зберігаються в одному спільному обмеженому SQLite-сховищі Durable Object, а інший об'єкт обмежує паралельні звернення до МКР. У локальному workerd через окремий тестовий проксі перевірено каталог, пошук, розклади групи та викладача; збережені копії пережили перезапуск локального сховища. Ці локальні тести не замінюють перевірку розгорнутого Cloudflare і Telegram на iPhone. Сайт джерела залишається HTTP.

06.11.2026 погоджений тестовий Worker став доступний за адресою `https://depara-vnau-test.yaroshandriy16.workers.dev/`. На реальному Cloudflare отримано 10 факультетів, 7 курсів факультету 7, 14 груп курсу 4 і пошук викладача; перевірено групу ЕІ-23-1 та викладача Бойка Олексія Романовича за 05–18.11.2026 (2 і 8 занять відповідно). Через помилку Cloudflare HTTP 530 для домену МКР транспорт використовує DNS-ім'я, що вказує на офіційний IP; перед використанням перевіряються обидві DNS-відповіді. Ця перевірка не шифрує HTTP МКР. Перевірка фізичного iPhone й Telegram Mini App залишається окремою.

## Майбутні сповіщення та обмеження збережених даних

Підготовлено тестову реалізацію фонового порівняння і підписок для `@DeParraTest_bot`, що працює і тоді, коли Mini App закритий. Фактичне надсилання потребує окремого секрету тестового бота, фонового Cron та наскрізної перевірки в Telegram. Значення секрету не записувати до GitHub і не передавати в чаті.

- Перевіряти кожну окрему групу чи кожного викладача, на розклад яких є підписка, спільно для всіх підписаних; не запитувати той самий розклад окремо для кожної людини. Дотримуватися помірного інтервалу та захисту від надмірних запитів до МКР.
- Зберігати підписку тільки після згоди користувача та перевірки підписаних даних Telegram на сервері; передбачити вимкнення сповіщень і видалення підписки. Зберігати мінімум потрібних даних: підтверджений ідентифікатор отримувача, ID групи чи викладача та налаштування. Неперевірені `initDataUnsafe` не використовувати для авторизації.
- Перша підтверджена копія є базою для наступного порівняння, а не приводом надсилати повідомлення про всі наявні заняття. Порівнювати лише підтверджені дані відповідного об'єкта й періоду; не вважати мережеву помилку, неповну таблицю чи зміну розмітки скасуванням занять. Уникати повторних сповіщень про ту саму зміну.
- Зберігати одну спільну копію розкладу на об'єкт і потрібний період, а також мінімальні дані для порівняння і підписок. Перед запуском сповіщень зберігати необхідні дані для активних підписок та їх порівняння; поточне тестове очищення не забезпечує цього. Не накопичувати без обмеження всі історичні розклади чи дублікати для кожного користувача.
- Попередні тижні й місяці показувати, доки відповідні розклади доступні у ВНАУ. За вибором користувача окремий постійний архів минулих розкладів або історії змін створювати не потрібно; очищення непотрібного кешу може позбавити доступу до старих дат, якщо джерело вже їх видалило.
- У тестовому Worker погоджено видаляти копії приблизно через 30–31 день без використання та обмежити спільні дані 512 записами і 5 МіБ JSON (службові дані SQLite додаються окремо). За перевищення ліміту найстаріші записи можуть видалятися раніше. На телефоні після успішного збереження нового розкладу прибираються непотрібні копії, що не використовувалися щонайменше 30 днів, а також найстаріші понад 20 записів або 1 МіБ. Профіль не видаляється. Python-сервер має окреме обмеження обсягу і не видаляє старі копії автоматично.
- Підготовлений Worker має окремий scheduled handler для перевірок, обмежене сховище підписок і останніх підтверджених копій, чергу та надсилання в тестовий бот. Окремий alarm звичайного кешу залишається лише очищенням і не є планувальником оновлення. До налаштування Cron і секрету реальні сповіщення не працюють.

Погоджено окремий тестовий Worker та робочу гілку GitHub; без нового погодження не змінювати основного бота та не публікувати інтеграцію в основній версії.

## Ручна перевірка джерела

1. Використати окремі публічні сторінки `/time-table/group?type=0` та `/time-table/teacher?type=0`. Для кожного отримання застосовувати власний `requests.Session`: один GET і потрібний POST із CSRF та cookies **цієї ж сесії**, кінцеві значення не логувати. Встановлювати timeout і зупинятися при помилках; не обходити автентифікацію, CAPTCHA чи обмеження сервісу.
2. Перший обмежений тестовий набір: максимум дві перевірені групи та два перевірені викладачі, послідовно, без паралельних запитів. Ідентифікатори, підтверджені у ході дослідження 05.11.2026: групи ЕІ-23-1 (`structureId=0`, `facultyId=7`, `course=4`, `groupId=3641`) і КН-24-1 (`structureId=0`, `facultyId=5`, `course=3`, `groupId=3878`); викладачі `teacherId=1847` і `teacherId=2264`. Перед повторним застосуванням перевіряти, що обрані ID та назви все ще відповідають формі джерела.
3. Діапазон ручного контрольного запиту — максимум 14 календарних днів, параметри `start` та `end` у `YYYY-MM-DD`, включно. Не запускати багато повторів; пауза між успішними запитами до джерела щонайменше 10 секунд. За помилки мережі або ознак блокування зупинятися, не повторювати у циклі.
4. Перед `status=success` парсер має перевірити, що отримано очікувану матрицю для запитаного об’єкта й повного діапазону дат, а не сторінку входу, помилку, порожню відповідь чи інший HTML. Порожній список занять вважати підтвердженим лише тоді, коли структура й усі запитані дати впізнані та в матриці немає жодного заняття. Нерозпізнане заняття або відсутній день — помилка, а не нуль пар. Події підгруп і паралельні заняття не зливати за часом.
5. Використати `integrations.vnau.cache.success_snapshot` тільки після успішної валідації. `failure_snapshot` зберігає останні підтверджені заняття й `lastSuccessAt` та оновлює `lastCheckedAt`, не публікуючи текст сирої помилки. `write_snapshot` перевіряє дані до атомарної заміни. Кеші груп і викладачів розділяти, наприклад `public/vnau/group/3641.json` і `public/vnau/teacher/1847.json`.
6. На реальних очищених зразках порівняти дати, час, повні назви, викладачів, групи/підгрупи й аудиторії з нормалізованим JSON. Окремо перевірити порожній день, накладені/паралельні пари, перехід місяця й видимі ознаки змін. Часовий пояс інтерпретації — `Europe/Kyiv`; не перетворювати дату `YYYY-MM-DD` на дату UTC.

## Альтернатива: статична публікація обмеженого набору

- Сторінка GitHub Pages може читати лише нормалізований HTTPS JSON, а не HTTP-сторінку МКР напряму. Один можливий шлях — ручний workflow, який послідовно формує перевірені JSON, зберігає попередній успішний кеш при помилках, збирає Vite з цими JSON і розгортає саме отриманий артефакт Pages. Наявний `.github/workflows/pages.yml` запускається вручну, тому простий коміт JSON **не оновлює** сайт.
- Для збереження кешу між чистими запусками потрібно явно вибрати перевірене постійне сховище. Якщо це файли у поточному репозиторії, потрібні контроль конкурентних запусків та розгортання того самого перевіреного стану, а також відсутність тригера `push`, який породив би цикл. Не змінювати код workflow на такий, що публікує кожен push.
- На першому запуску перевірити розгорнуті HTTPS JSON: правильний ID та назва, `schemaVersion`, `sourceKind`, `lastSuccessAt`, реальні дати й заняття, відсутність секретів; перевірити інтерфейс, правильний статус для кожного об’єкта і fallback на перевірений кеш. Тільки після цього окремо узгодити помірний cron (раз на 2–3 години) та реальний список об’єктів; не додавати cron до успішного ручного тесту.

## Важлива межа статичного сайту

Вибір групи чи викладача зберігається локально у браузері; GitHub Actions не бачить цих виборів і не може сам вирішити, чиї розклади запитувати. Статичний Pages і обмежений заздалегідь узгоджений manifest можуть обслуговувати лише об’єкти, для яких JSON вже підготовлено; для інших треба показати чесний стан «дані недоступні». Для довільного вибору потрібні окремо погоджені архітектура реєстрації виборів/сервер або попередньо перевірений каталог і масштабна стратегія синхронізації з дотриманням обмежень джерела. Не збирати весь каталог і тисячі викладачів автоматично без перевірки й окремого рішення.

Аналогічно, публічний пошук викладачів МКР виконується на сервері джерела, а результати одного перевіреного запиту обмежені 200 записами без підтвердженої пагінації. Статичний браузерний каталог не можна назвати повним, доки його повнота не перевірена. Пошук у локальній частковій вибірці потрібно позначати як частковий; прямий браузерний запит до HTTP МКР не використовувати.

## Підготовлений обмежений пілот

`python -m integrations.vnau.pilot --group 3641 --teacher 1847 --start 2026-11-05 --end 2026-11-18 --output-dir out/vnau-pilot` збирає дані тільки для явно вказаних перевірених ID. Пілот зупиняється після помилки джерела та не публікує результат. Дозволений набір ID обмежено переліком у `pilot.py`; це не каталог університету. Діагностичний workflow має ручний режим `pilot`, що зберігає нормалізовані JSON у короткоживучий артефакт. Цей артефакт ще не є кешем GitHub Pages і не робить інтеграцію доступною користувачам Mini App.
